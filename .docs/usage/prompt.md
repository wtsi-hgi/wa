Spec the mlwh server storing usage metrics, broken down by CLI, MCP and other API usage, including things like (per time period) num unique clients, num queries per client/"session", num calls per endpoint. Give server admin simple access to understand the usage metrics. Suggest following a similar pattern on how feedback was implemented. Note that I don't really know what can be determined from callers, so take my suggestions prior with a pinch of salt, but at least in general I want admins to know the system is being used and which endpoints are most popular.

## Notes

### Findings from codebase research

- Today the server cannot tell CLI from MCP callers or distinguish sessions or users. The CLI and the MCP server both use `mlwh.RemoteClient`, which sets no User-Agent (Go default `Go-http-client/1.1`) and no identifying headers. The Next.js web UI's `fetch` sends `User-Agent: node`.
- The only request logging is go-authserver's stderr access log. Nothing is stored.
- `wa mlwh serve` does not host MCP. The MCP server lives in the separate repo `/home/ubuntu/llm-knowledge-base` (`mlwh-mcp-server`). It imports wa and calls wa over REST through a single shared `mlwh.RemoteClient`. In shared HTTP mode every MCP user arrives from the MCP host's IP. Per call, the MCP server knows the agent clientInfo (name/version), transport, its own version, and the go-sdk session ID (see `internal/mlwh/tools_feedback.go`).
- In practice there is no per-user auth identity: secured mode only accepts the server owner's token.
- Registry endpoints are all registered through `registerMLWHEndpoints` in `mlwh/server.go`, so one middleware keyed on the gin route template (`c.FullPath()`) can count them.
- The agent feedback feature (`.docs/feedback/spec.md`; `mlwh/feedback*.go`, `WithFeedback`, `openMLWHServeFeedback`, `frontend/lib/feedback-admin.ts`, `/feedback` page, auth-menu link, run-dev.sh wiring, verify-wa recipes) is the pattern to mirror. The feedback spec had a companion spec in `llm-knowledge-base`; this feature needs one too.

### Decisions

- Callers identify themselves through optional request headers. `mlwh.RemoteClient` gains a configurable User-Agent and per-request headers. The CLI sends `wa-cli/<version>`, a per-invocation run ID, and the OS username. The web UI sends `wa-web` and forwards the logged-in user's username. A companion spec in `llm-knowledge-base` makes the MCP server send `mlwh-mcp-server/<version>`, its transport, a per-session ID (a hash of the go-sdk session ID), the agent's clientInfo name/version, the MCP tool name, and a username where it has one. Usernames are self-declared and spoofable; the admin view should present them as such. Requests without these headers count as "other API".
- Categories are CLI, MCP, web, and other API, plus a category for each other caller that can be usefully and accurately identified. In particular wa's own servers that call the MLWH server through `RemoteClient` get their own category: `wa results serve` sends `wa-results-server/<version>` and `wa mlwhdiff serve` sends `wa-mlwhdiff-server/<version>` (the `wa mlwhdiff diff` CLI shares the constructor, so the CLI vs server label is set at each call site; the CLI use counts as CLI). The spec author should identify any other caller that can be categorised accurately; "other API" is only for callers that cannot be identified. Internal-server calls do not carry the originating end user or session.
- Each counted request records: timestamp, category, route template (never actual path or query values), client/run/session ID, username if sent, socket IP (never `X-Forwarded-For`), User-Agent-derived client version, MCP tool name if sent, HTTP status code, and latency. `/health` and the admin/usage routes are not counted; Registry calls, `POST /feedback` and `/openapi.json` are.
- Storage is one row per request; aggregates are computed at query time.
- Rows older than a configurable number of days (default 365) are pruned automatically.
- Usage is stored in its own SQLite file, enabled by `--usage-db` / `WA_MLWH_USAGE_PATH`, mirroring the feedback store setup. Usage tracking is off when unset.
- Admins view usage through a token-protected admin JSON endpoint plus a Next.js `/usage` page reusing the feedback admin token handling and `WA_FEEDBACK_ADMINS` allowlist, with an auth-menu link. No CLI for now.
- The page offers preset windows: last 24 hours, 7 days, 30 days, all time. For the chosen window it shows requests by category, unique clients/sessions/users, requests per session (median and max), top endpoints (and top MCP tools), and a per-day trend.
- The page shows trends across the whole history, not just the latest window. For the chosen window length (24 hours, 7 days, 30 days), it shows a series of consecutive windows of that length going back from now to the earliest stored record (e.g. each 30-day period back to the start of records), so an admin can see at a glance that usage rose, fell, or stopped (e.g. "used in the previous 30 days, but nobody used it in the most recent 30 days"). The series is shown overall, per category, and per endpoint. Retention pruning bounds how far back the series reaches. "All time" has no series of its own beyond the per-day trend.
- The web UI gives each browser an anonymous random cookie; Next.js forwards a hash of it as the web session ID, so anonymous web sessions are counted. The server-wide cached `/studies` fetch (`lib/studies-cache.ts`) carries no session or user.
- CLI and MCP users cannot opt out of sending their username; document it as self-declared metadata.
- Day buckets and window boundaries use UTC.
- For MCP calls the server records the agent identity the MCP server forwards (clientInfo name/version in stdio, the agent's HTTP User-Agent in HTTP mode), and the MCP breakdown shows top agents.
- The server stores the raw User-Agent (truncated to a fixed length) for every counted request, and the "other API" breakdown shows top User-Agents.
- `run-dev.sh` readiness polling (curl of `/freshness` and `/studies`, in every mode including prod) sends its own User-Agent (`wa-run-dev`), and the server does not count requests with that User-Agent. This is accepted even though any caller could spoof it to avoid counting. verify-wa curl traffic is not special-cased; it counts as other API.
- Unique-client counts use the client/run/session ID where one is sent; requests with no ID (other API, internal servers) fall back to socket IP, and the page labels those counts "by IP".
- `wa results register` reaches the MLWH server only via `wa results serve`, so it counts under the results-server category. No other callers of the MLWH server exist on this machine.
- For the chosen window the page also shows error count and rate per category and per endpoint, and median and p95 latency per endpoint.
- Requests that match no route (404 with empty `c.FullPath()`) are counted too, so admins can spot LLMs hallucinating endpoints through MCP, docs mistakes, or callers still using a changed/removed endpoint. Because they have no route template, these rows store the actual request path (query string stripped, truncated to a fixed length) as the one exception to "never actual path values". The page shows top unmatched paths with counts, broken down by category (and by MCP tool/agent where sent). 404s from matched routes (e.g. an unknown sample ID) are counted under their route template like any other status. Requests rejected by auth before reaching a handler (401 in secured mode) are not required to be counted.
- For the chosen window the page shows a "top users" table and a "top clients" table with request counts, broken down by category. Usernames are labelled self-declared; clients without an ID are shown by IP and labelled "by IP".
- Web counts reflect requests that reached the MLWH server, not page views: the web UI's per-browser cookie cache (`wa-seqmeta-cache`, `frontend/lib/mlwh-cache-*.ts`) and the server-wide `/studies` cache serve some lookups without a server call. The page or docs say so; cache hits are not counted.

### Further findings

- `wa` has no version flag or ldflags stamping; `debug.ReadBuildInfo().Main.Version` reports the git-tag version (e.g. `v0.10.1+dirty`) and can fill `wa-cli/<version>`.
- Current release is `v0.10.1`, `APIVersion` `1.9.0` (`mlwh/openapi.go`). Feedback admin routes are not in OpenAPI; only `POST /feedback` is.
- `/openapi.json`, `/health` and `POST /feedback` are not registered through `registerMLWHEndpoints`, so the counting middleware must sit at router level and skip excluded routes.
- The admin token is currently only created/read when feedback is enabled; it must also be available when only usage is enabled.
- CLI call sites building a `RemoteClient`: `cmd/mlwh_info.go`, `mlwh_latest.go`, `mlwh_search.go`, `mlwh_runs.go`, `mlwh_export.go`, `mlwh_studies.go`, `mlwhdiff.go`. `wa results serve` builds one at `cmd/results.go`.
- Web UI MLWH calls all go through `mlwhJson` in `frontend/lib/backend-client.ts`; per-user calls come from Server Actions in `app/(results)/actions.ts`, where `session.username` is available (null when anonymous).
- MCP (go-sdk v1.6.1): HTTP mode runs `Stateless: true`, so `ClientInfo` is unavailable there; send the agent's HTTP User-Agent instead (as feedback does). In stateless HTTP mode `req.Session.ID()` is the client-echoed session ID and is stable per client session. In stdio `Session.ID()` is empty, so generate a random ID per process. HTTP mode has no auth, so never a username; stdio can send the OS username. The provider shares one client across callers, so per-call headers (tool name, session) must travel per request (e.g. via context), not as client config.
- run-dev.sh feedback DB wiring to mirror uses `WA_MLWH_FEEDBACK_PATH`; test mode uses a throwaway temp file deleted on shutdown.
- In secured mode `EnableAuthWithServerToken` runs before `RegisterRoutes`, and gin groups copy their handler chain at creation, so a later `router.Use(...)` does not reach Registry routes under the auth group. The counting middleware must be placed so it covers the plain router, the auth group, and unmatched (NoRoute) requests.
- Feedback admin routes register on the plain router with their own token check (`registerFeedbackAdminRoutes` in `mlwh/feedback_server.go`) and are not in OpenAPI; the usage admin endpoint follows the same pattern.
- `mlwhJson` is called from both `frontend/app/(results)/actions.ts` and `frontend/app/(results)/feedback/actions.ts`; both must send the web headers.
- No privacy/cookie notice exists in the frontend or docs; existing cookies are functional (`frontend/lib/results-auth-cookie.ts`, `wa-seqmeta-cache`). Docs should state the new anonymous cookie is used only for usage counting.
- Past specs bump `APIVersion` in `mlwh/openapi.go` when the API surface changes; documenting the new optional identification headers in OpenAPI implies 1.9.0 -> 1.10.0, with the usage admin route kept out of OpenAPI like feedback's admin routes.
- As with feedback, this wa spec owns the wire contract (identification headers). The companion MCP spec at `/home/ubuntu/llm-knowledge-base/.docs/usage/spec.md` consumes it and is written separately; this spec only needs `RemoteClient` to support it (configurable User-Agent and per-request headers, e.g. via context, since one client is shared across MCP sessions).
- A failed usage write must never fail or noticeably slow the request being counted.
